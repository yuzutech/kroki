= Maintainer guide

This guide describes the tasks the maintainers perform to keep Kroki up to date and to release it.

== How to prepare a release

Renovate only bumps the version declared in the dependency manifests (`package.json`, `deno.json`, `Dockerfile`, `pom.xml`...).
The assets copied from `node_modules` (such as `mermaid/assets/mermaid/` and `bpmn/assets/bpmn-viewer.production.min.js`) are not committed: the companion images generate them at build time.
But Renovate does not propagate the versions everywhere else, so the following steps are mandatory before triggering the https://github.com/yuzutech/kroki/actions/workflows/release.yml[Release workflow]:

. from an up-to-date `main` branch, run `task updateVersions`
+
This command reads the versions of the diagram libraries (`package.json`, `deno.json`, `Dockerfile`, `Cargo.toml`, `pom.xml` and `diagrams.net/assets/js/app.min.js`) and updates `docs/antora.yml` and the `getVersion()` method of each Java service accordingly.
. check that the versions match the updated libraries (`git status`, `git diff`)
. add an entry for each updated diagram library under `### Diagram libraries` in the `## [Unreleased]` section of `CHANGELOG.md`
. open a pull request with these changes and merge it before triggering the Release workflow

== How to update third-party dependencies

Most third-party dependencies are pinned in `server/ops/docker/Dockerfile` through an `ARG <NAME>_VERSION` variable.

[IMPORTANT]
====
After bumping a version in the `Dockerfile`, always run `task updateVersions`.

This command reads the `*_VERSION` arguments from `server/ops/docker/Dockerfile` and propagates them everywhere the version is referenced (such as `docs/antora.yml` and the `getVersion()` method of the corresponding Java service) so that everything stays in sync.
====

=== blockdiag (and actdiag, nwdiag, packetdiag, rackdiag, seqdiag)

We are building a single binary with Nuitka from a fork, https://github.com/yuzutech/blockdiag, in `tools/blockdiag/Dockerfile`.
The upstream project looks abandoned, and the fork works with recent Python versions and reads/writes stdin/stdout in CLI mode.
The binary is published as a container image, `ghcr.io/yuzutech/kroki-builder-blockdiag:<version>`, so building Kroki only copies it.

When a new version is available, we need to:

. update the fork and tag the new version (`vx.y.z`)
. update `ARG VERSION` in `tools/blockdiag/Dockerfile` (Renovate opens this pull request, which runs the "Tool images" workflow to build and test it on amd64 and arm64)
. run the "Tool images" workflow with the tool `blockdiag` and the new version: https://github.com/yuzutech/kroki/actions/workflows/tool-images.yml
. update the image tag in `FROM ghcr.io/yuzutech/kroki-builder-blockdiag:<version> AS blockdiag` in `server/ops/docker/Dockerfile` (Renovate opens this pull request too)
. run `task updateVersions` (see above)

==== C4-PlantUML (bundled model files)

The `C4 with PlantUML` diagram type uses the https://github.com/plantuml-stdlib/C4-PlantUML[C4-PlantUML] macro library. Because PlantUML runs in `SAFE` mode (no remote `!include`), the library files are vendored under `server/src/main/resources/` and concatenated into the diagram source by `Plantuml.sanitize()`. Vendored file names are the lower-case upstream names: `C4.puml` -> `c4.puml`, `C4_Context.puml` -> `c4_context.puml`, and likewise for `Container`, `Component`, `Deployment`, `Dynamic` and `Sequence`.

When a new version is available, we need to:

. copy each upstream file from the release tag (e.g. `https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/v<x.y.z>/C4_Context.puml`) over the matching resource file
. in the six sub-files (all except `c4.puml`), delete the include guard upstream puts at the top — it resolves to a remote URL that `SAFE` mode rejects:
+
[source]
----
!if %variable_exists("RELATIVE_INCLUDE")
  !include ./C4_Context.puml
!else
  !include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/.../C4_Context.puml
!endif
----
. make no other edits: the files are inlined verbatim, so every remaining line must stay exactly as upstream. Verify with `diff <(curl -sL <raw-url>) server/src/main/resources/<file>` — only the guard block above may differ
. bump the version assertion in `server/src/test/java/io/kroki/server/service/C4PlantumlServiceTest.java` to the new version
. run `./mvnw -q -pl server test -Dtest=C4PlantumlServiceTest` (renders C4 diagrams through the inlined bundle; `linux/amd64` only, like CI)

=== UMLet

We are building a native binary with GraalVM from the `mini` branch of a fork, https://github.com/yuzutech/umlet, in `tools/umlet/Dockerfile`.
The fork strips UMLet down to its rendering engine and adds a command line interface that reads from stdin and writes to stdout.
The binary loads the AWT shared libraries generated next to it, so the image contains the whole `/opt/umlet` directory.
It is published as a container image, `ghcr.io/yuzutech/kroki-builder-umlet:<version>`, so building Kroki only copies it.

When a new version is available, we need to:

. update the `mini` branch of the fork
. update `ARG VERSION` (UMLet version) and `ARG REVISION` (commit of the `mini` branch) in `tools/umlet/Dockerfile`, the pull request runs the "Tool images" workflow to build and test it on amd64 and arm64
. run the "Tool images" workflow with the tool `umlet` and the new version: https://github.com/yuzutech/kroki/actions/workflows/tool-images.yml
. update the image tag in `FROM ghcr.io/yuzutech/kroki-builder-umlet:<version> AS umlet` in `server/ops/docker/Dockerfile`
. run `task updateVersions` (see above)
